# 文档设计稿 — 安卓无障碍自动化双 App 技术改进文档

## ① 读者与目标

- **读者**：接手这两个项目的工程师（可能没参与过本轮改进）
- **目标**：让他读完能 ① 说清两个 App 的架构分层 ② 理解每个关键决策的**理由**（不是"怎么做的"）③ 遇到同类问题知道怎么查
- **不追求**：API 逐个罗列（那是 README 的活）；本篇只写**为什么**和**代价**

## ② 核心叙事（这是全文的骨架）

两个 App 表面是"私信助手"和"恋爱键盘"，本质是**同一个内核的两层封装**：

```
内核：感知(看见) → 决策(想) → 执行(做) → 交互(人在回路)
```

本轮所有改进都落在这四层里的某一层。因此文档按**层**组织，而不是按 App 组织；
每个小节末尾用「私信助手 / 恋爱键盘」两栏说明各自落地情况。

## ④ 写作纪律（对齐 PPT 的 anti_pattern）

- ❌ 不写"我们做了 X 功能"的功能清单式流水账 → 写"为什么这样选，代价是什么"
- ❌ 不裸列行列文字 → 关键对比一律上表
- ❌ 不写"暂无问题"式的空章节 → 遗留必须写清**为什么暂时不做**
- ✅ 每个技术决策至少给一条**实测数字**或**真实报错原文**
- ✅ 问题现场章节是全文最有价值的部分，篇幅占比不低于 20%

### 模型选型实测
| 模型 | 耗时 | 输入价/百万token | 结论 |
|---|---|---|---|
| glm-4.5v | 40–57 s | 2 元 | 太慢且贵 |
| glm-4.6v | 5.8–8.4 s | 1 元 | 主力 |
| GLM-4.6V-Flash | 9–12 s | 免费 | 偶发 429 |
